〇 必读：boot-args 必须加这 6 项

这是硬性要求，不是可选优化。光把 kext 装进 /Library/Extensions 不够 —— install.sh 只拷文件，不改 OpenCore。缺了就是黑屏。

boot-args 里必须有这 6 项，一项都不能少：

nvfb=1  nvaccel=1  nvfbheads=4  -nvkmsnosmooth
amfi_get_out_of_my_way=0x1  amfi=0x80

ipc_control_port_options=0 不是必需的，先别加 —— README 把它列进了推荐串，但已实测有机器加上去直接 panic。 它只跟 Firefox 启动崩溃有关，跟显示链路无关。要试也放到最后单独试。

并且不能有 nv_disable=1 或 -wegnoegpu。

参数作用缺了会怎样
nvfb=1 NVRMFB 的启动开关（nvrm-fb.cpp:2145，源码注释叫 boot-loop guard） NVRMFB 直接 NOT starting → 没有任何 framebuffer → 黑屏
nvaccel=1 NVAccel 加速器的启动开关（nvrm-accel.cpp:593） 没有 2D/3D 加速、没有 Metal 合成 → 桌面卡顿或起不来
nvfbheads=4 发布几个显示 nub（NVRM.cpp:70，默认 1，上限 4） 只发 1 个 → 多显示器 / 多 head 的面板点不亮
-nvkmsnosmooth 关掉「平滑接管」：不再复刻固件当前的显示时序，让 NVKMS 自己重新设模式（NVRM.cpp:583） 走 smooth takeover 路径，部分机器上花屏 / 黑屏
amfi_get_out_of_my_way=0x1 关掉 AMFI 的代码签名校验（Apple 参数，不是驱动的） WindowServer 加载不了未签名的 NVMTLDriver.bundle → 没有 Metal
amfi=0x80 同上，放宽库校验（Apple 参数）
ipc_control_port_options=0
先别加		 放宽 Mach IPC 控制端口限制（Apple 参数）。只为修 Firefox 启动崩溃，与显示无关 缺了不影响驱动；但已实测有机器加了直接 panic，所以默认不加

缺 nvfb=1 的症状：四个 kext 全都加载、NVRM 也打印 PASS 2 REACHED， 但 NVRMFB 直接 boot-arg nvfb=1 absent: NOT starting —— 屏幕全黑，看起来像驱动坏了。

要改的地方：EFI/OC/config.plist → NVRAM → Add → 7C436110-AB2A-4BBB-A880-FE41995C9F82 → boot-args， 并且把 boot-args 同时加进 NVRAM → Delete （只加 Add 不加 Delete 无效，变量已存在时 OpenCore 不会覆盖）。

⚠ 两个常见报错

① command not found / permission denied

文件明明在，但 sudo ./nm185-diag.sh 报 command not found，直接 ./nm185-diag.sh 报 permission denied —— 因为下载下来的脚本没有执行位（默认 644）。./xxx.sh 要求 +x，bash xxx.sh 不要求。

cd ~/Desktop
sudo bash nm185-diag.sh

看手册不用 sudo，也不用执行位：bash nm185-diag.sh --guide

② curl 被重置（Connection reset by peer）

ping github.com 通、curl 却被 Recv failure: Connection reset by peer 掐断 —— 说明网络是通的，只是终端没走代理。

curl 不读 macOS 的系统代理设置（系统设置里勾了也没用），它只认环境变量。代理软件开着 ≠ 终端走代理。

整段粘贴这个就行（自动读系统代理端口 → 下载 → 直接打印手册，不用自己填端口）：

P=$(scutil --proxy | awk '/HTTPSProxy/{h=$3}/HTTPSPort/{p=$3}END{if(h&&p)print h":"p}')
[ -n "$P" ] && export https_proxy=http://$P http_proxy=http://$P; echo "proxy=${P:-none}"
curl -fsSL https://raw.githubusercontent.com/GeekAudio/nm185-diag/main/nm185-diag.sh -o /tmp/nm185-diag.sh || \
curl -fsSL https://cdn.jsdelivr.net/gh/GeekAudio/nm185-diag@main/nm185-diag.sh -o /tmp/nm185-diag.sh
bash /tmp/nm185-diag.sh --guide

看到 proxy=127.0.0.1:7897 这种就说明代理接上了；proxy=none 说明系统里没配代理，得先开代理软件的「系统代理」。

实在搞不定就别下载了。让群友把 nm185-diag.sh 直接发给你，存到 /tmp，再 sudo bash /tmp/nm185-diag.sh。脚本就一个文件，不依赖任何东西。

bar1@0x14 在不在，就是"真 BAR1 aperture 在不在"的唯一判据。24 MB 装不下 2560×1600 的 16 MB surface，WindowServer 所以崩。

二 安全网

改 ResizeGpuBars 有开不了机的风险。先确认至少有一条后路：

  • 1401 的 Remove NVIDIA driver 启动项可用
  • 或 U 盘里有一份能启动的 EFI 副本
  • 或能把硬盘拆到别的机器上挂 ESP

都没有就先别改，只做 E0。

随时回退：boot-args 末尾加 -nvoff（驱动总开关），系统就回到普通黑苹果状态。

三 E0：用 2.3.5 复测 5 分钟 · 零风险

不改任何配置，只确认后半段阻塞还在。跑一次 sudo bash /tmp/nm185-diag.sh，看输出末尾的「驱动:」和「nvrm-bars」两行。

  • 仍无 bar1@0x14 → 阻塞还在，继续 E1
  • 预算不再是 24 MB → 中间版本动过 BAR1 路径，先回报
  • 桌面居然起来了 → 已修好，只需更新 issue

四 E1：BAR 放置矩阵 关键

源码 NVRM.cpp:1031-1053 有一段专为 #185 写的跳过逻辑，三个条件缺一不可：

if (!newSize) {                        // BAR1 已 >= 4 GB
  if (cur1 >= 4GB && inNub && !conInside) {
     return true;                      // 不搬，保住 aperture
  }
}

现有日志显示它没触发，但不知道是哪个条件为假。这组实验就是把三种可能拆开。

改哪里：OpenCore 的 EFI/OC/config.plist，两个键不在同一节：

  • ResizeGpuBars → UEFI → Quirks（固件层，决定固件给 GPU 多大的 BAR）
  • ResizeAppleGpuBars → Booter → Quirks（macOS 引导层）

用 ProperTree 或 OCAuxiliaryTools 打开，只改这两个整数，其它别动。

组 C 已经有过一次「改完起不来」的记录。做之前先把安全网走一遍。
